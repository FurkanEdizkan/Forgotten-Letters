## Features

### Create a campaign (`campaign_create`)

**An Owner or Admin creates a campaign in a six-step wizard and becomes its Campaign Master.**

1. admin → areas: wizard: basics, schedule, seats, house rules, review
2. areas → campaignService: create
3. campaignService → repos: insert campaign, CM member, seats
4. repos → campaignTables: one transaction
5. campaignService → auditService: record campaign.created

### Compendium (`compendium`)

**Anyone signed in reads the rules by version: sections like the Trench Companion compendium, a page per element with every link in and out, keyword pop-ups and a neighbourhood graph.**

1. user → areas: open /rules, search, open an element
2. areas → rulesService: search, node with edges, diff
3. rulesService → repos: nodes and edges by set
4. areas → rulesLib: render text links, lay out the graph

### Fighter card (`fighter_card`)

**The Owner uploads a frame per faction; a player opens a fighter's card, drawn in the browser from the fighter's
photo, its data and its faction's frame, and saves it as a PNG.**

1. user → areas: Owner: upload or remove a frame
2. areas → cardFrameService: setFrame / clearFrame
3. cardFrameService → rulesService: is the target a loaded faction, variant or Sin
4. cardFrameService → repos: upsert card_frames
5. repos → warbandTables: card_frames
6. cardFrameService → auditService: record card_frame.set / removed
7. user → areas: player: fighter → Card
8. areas → warbandService: the warband view: stats, frame URL, seat
9. warbandService → cardFrameService: frame for the resolved faction
10. areas → cardFrameService: GET /uploads/frames/[id]

### First start: migrations, backup, the setup wizard (`first_start`)

**A group installs the app and sets it up in the browser, Jellyfin style, without editing files.**

1. server → hooks: load the built app
2. hooks → backupService: dump before migrating
3. hooks → infra: apply migrations under a lock
4. hooks → setupService: no owner: log that setup is open
5. hooks → settingsService: listen on the stored port
6. visitor → publicPages: opens any page, lands on /welcome, presses Setup, fills the four steps
7. publicPages → setupService: finish: owner, look, port
8. setupService → repos: lock settings, insert owner, save settings
9. setupService → authService: start a session
10. setupService → auditService: record the first owner

### Homebrew factions (`homebrew`)

**A player creates their own faction, variant or items with custom rules, in the rules folder format, and builds warbands with it.**

1. user → areas: new homebrew, edit units and armoury, share
2. areas → homebrewService: create / update / share
3. homebrewService → rulesLib: check
4. homebrewService → repos: save with a version check
5. repos → homebrewTables: homebrew_sets
6. homebrewService → rulesService: index as set hb:<id>
7. admin → areas: campaign settings: allow homebrew
8. areas → campaignService: update homebrewSets
9. campaignService → rulesService: check it builds on the campaign's rules
10. user → areas: new warband on homebrew, assign to seat
11. areas → warbandService: create / assign (only if allowed)

### House rules from the library (`house_rules`)

**The CM drags preset rules (or writes their own) into the campaign's house rules and sets their values; players see them on the campaign page.**

1. admin → areas: drag a preset or press Add, set values, save
2. areas → campaignService: create / update with houseRules
3. campaignService → repos: save house_rules (version check)
4. repos → campaignTables: campaigns.house_rules
5. campaignService → auditService: record campaign.updated
6. user → areas: campaign page lists the rules with their values

### Invite and join (`invite_and_join`)

**Nobody registers alone: an owner or admin sends a link that fixes the role.**

1. admin → areas: create an invite (role, note)
2. areas → inviteService: create
3. inviteService → repos: insert invite
4. inviteService → auditService: record invite
5. visitor → publicPages: opens /invite/<token>, chooses username and password
6. publicPages → inviteService: accept
7. inviteService → repos: lock invite, insert user, mark used
8. inviteService → authService: start a session

### Ask to join, then approve (`join_request`)

**Anyone signed in can ask to join a listed campaign while it is mustering; the CM or a co-CM places them.**

1. user → areas: ask to join (optional note)
2. areas → joinRequestService: request
3. joinRequestService → repos: insert open request
4. admin → areas: approve into a seat
5. areas → joinRequestService: approve
6. joinRequestService → repos: lock seat, fill it, mark approved
7. joinRequestService → auditService: record request.approved

### Managing people (`managing_people`)

**The owner keeps the group's accounts in order without email.**

1. owner → areas: change role, disable, reset, anonymise
2. areas → peopleService: apply
3. peopleService → repos: update user (version checked)
4. peopleService → authService: end sessions
5. peopleService → auditService: record change

### Failure and recovery (`failure_and_recovery`)

**A group without an ops person can see what is wrong and get back on its feet.**

1. owner → health: checks /health/ready
2. health → infra: ping the database, migrations applied
3. owner → areas: download or restore a backup
4. areas → backupService: dump or restore
5. backupService → infra: pg_dump, pg_restore

### Load the rules folders (`rules_load`)

**At start, and when the Owner presses Reload, the app reads every rules version folder, checks it and caches its elements and links.**

1. owner → areas: Owner, Rules data: Reload
2. areas → rulesService: reload
3. rulesService → rulesLib: parse, check, derive edges
4. rulesService → repos: replace the cached sets, nodes and edges
5. repos → rulesTables: one transaction

### Join by seat link (`seat_join`)

**The CM makes a lasting link for a seat and copies it from the seat's card; the person who opens it takes that seat, with a new account if needed.**

1. admin → areas: make link (one seat or all empty seats)
2. areas → seatService: makeLink
3. seatService → repos: revoke open link, insert hash and encrypted link
4. admin → areas: seat card: copy link; withdraw one or all links
5. areas → seatService: copyLink / revokeLink / revokeAllLinks
6. seatService → auditService: record seat.link_copied
7. visitor → publicPages: opens /join/<token>, signs in or creates an account
8. publicPages → seatService: preview (sets opened_at once), then accept
9. seatService → authService: rate limit, new account, session
10. seatService → repos: lock link, fill seat, mark used
11. seatService → auditService: record seat.joined

### Sessions and the account page (`sessions`)

**Everyone controls their own sign-in.**

1. user → hooks: any request with the cookie
2. hooks → authService: resolve session
3. authService → repos: read session, slide expiry
4. user → areas: change password, sign out everywhere
5. areas → authService: change password, end sessions

### Instance settings: text size, accent and port (`instance_settings`)

**The Owner changes how the copy looks and where it listens, from the browser.**

1. owner → areas: opens /owner/settings, changes text size, accent or port
2. areas → settingsService: save
3. settingsService → repos: update the settings row
4. settingsService → infra: port changed: move the listener
5. infra → server: open the new port, close the old one
6. settingsService → auditService: record the change

### Sign-in: one screen for every role (`sign_in`)

**Owners, admins and users sign in on the same screen and land in their own area.**

1. user → publicPages: username, password, remember me
2. publicPages → authService: signIn
3. authService → infra: rate limit
4. authService → repos: find user, create session
5. authService → auditService: record sign-in
6. publicPages → user: cookie, redirect to the role area

### Build a warband (`warband_build`)

**A player builds a warband like the Trench Companion builder, by the books: faction (with its variant or Sin), name and
starting banks; then fighters and their kit on a two-column page, checked on every change; the Arsenal, campaign data
and play mode; then assigns it to their campaign seat.**

1. user → areas: new warband, add fighter, equip, move, sell, campaign data, play
2. areas → warbandService: create / recruit / equip / move / sell / refund / status / xp
3. warbandService → rulesService: the warband's rules set
4. warbandService → warbandEngine: check the change, sell value, refund window, progression
5. warbandService → repos: save with a version check
6. repos → warbandTables: warbands, fighters, Arsenal
7. user → areas: assign to my seat
8. areas → warbandService: assignToSeat
9. warbandService → campaignService: my seat, allow beyond limits, CM for the patron
10. warbandService → auditService: record warband.assigned
