## Features

### Access and sign-in (`access_and_sign_in`)

**Two modes, two doors.** `ACCESS=open` (a LAN at the venue) lets anyone watch the map;
`ACCESS=private` (deployed; set by build_and_update.sh when DOMAIN is set) shows a
signed-out visitor only the doors: /login, /admin/login and /join/<invite>. Pages
redirect there, data answers 401.

1. cm → hooks: GET /admin (signed out)
2. hooks → access: accessFor: CM-only, signed out
3. hooks → cm: redirect /admin/login?next=/admin
4. cm → door: POST /admin/login: username, password, remember
5. door → accounts: signIn(event, cm): per-address limit, authenticate, right door?
6. accounts → t_accounts: check the hash, create a session
7. accounts → audit: signin.ok / signin.fail
8. accounts → access: landingFor: next if allowed, else /admin
9. door → cm: Set-Cookie cf_session, 303 to /admin
10. cm → hooks: next request with the cookie
11. hooks → accounts: sessionUser: cached in Redis, renewed once a day
12. hooks → access: accessFor: allow

### Campaign flow (`campaign_flow`)

**From founding to the final reckoning.** Stages run setup → mustering → underway →
ended (`campaign-flow.ts`, shared by server and pages).

1. cm → admin: found the campaign, set the seats
2. admin → campaign: ensureSeats, issueInvite
3. player → door: follow the invite link
4. door → campaign: redeemInvite: account + seat
5. player → public: muster: found the warband, pick a Vision
6. cm → admin: advance to under way
7. player → public: the round: roll, pick an opponent and a field
8. public → api: /api/round
9. api → campaign: one locked step at a time (rounds.ts)
10. cm → admin: record the battle
11. admin → campaign: commitGame, closeRoundIfDone
12. campaign → engine: replay the events: standings

### Live map (`live_map`)

**Every screen follows the campaign within a second.** A change anywhere (a battle
recorded, the weather turned) reaches every phone and the TV without a reload.

1. cm → admin: records a battle
2. admin → campaign: commitGame
3. campaign → t_campaign: writes the game
4. admin → server.live: publish(campaign): it changed
5. admin → world: announceResult: the battle-result effect
6. world → server.live: sendTrigger: one-shot, to every screen
7. hooks → server.live: after any write: snapshotStale (bump the generation)
8. server.live → redis: pub/sub to every instance
9. server.live → api: each /api/stream re-sends the snapshot
10. api → ui.live: SSE: snapshot (100 ms after a change), clock, trigger
11. ui.live → livemap: new state; the trigger flies to the zone and plays the result
12. livemap → fx: weather, battles, monuments
13. livemap → guest: the map moves

### Warband builder and Trench Companion import (`warband_builder`)

**Every warband follows the books.** The rules come from book packs: complete Faction Studio files
for each faction and variant (units, armoury, upgrades, faction rules, keywords), read from the
group's own copies of the books and loaded in Admin → Rules. The builder checks each recruit,
purchase and upgrade against them.

1. cm → admin: Admin → Rules: load the book packs
2. admin → rules: readPacks, loadPacks (verified book rows)
3. rules → t_rules: units, armoury, faction rules, keywords
4. player → public: Import from Trench Companion (link, text or JSON)
5. public → warbands: readTcSource, importInto
6. warbands → engine: fromTcText / fromTrenchCompanion, matchToBook
7. warbands → t_rosters: replace the roster, fireteams
8. warbands → engine: warbandIssues: what the books find wrong
9. player → public: recruit, buy, upgrade
10. public → engine: recruitCheck, equipCheck (priceFor), upgradeCheck: no action may break a limit
11. player → public: record the aftermath: Trauma, Promotion and Advancement rolls
12. public → warbands: aftermath report (server-rolled)
13. warbands → t_campaign: aftermath_report
14. cm → admin: approve the aftermath
15. admin → warbands: apply the report to the roster
